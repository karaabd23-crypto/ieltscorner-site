> ## Correction added 2026-10-05, after this report was first published
>
> Everything below this box was written before the site owner pulled live
> Search Console data the same day. That data supersedes the headline claim
> of this report (**"0 of 477 indexed, 12 straight weeks"**) and one
> follow-up code claim made in conversation. Both corrections:
>
> **1. Indexing is not 0 — it's 80, with a real backlog behind it.** The
> `sitemaps[].indexed` field this report (and the ten before it) led with is
> an unreliable metric from the Sitemaps API's own submitted/indexed
> reconciliation, not the real Index Coverage status — it read 0 for 12
> straight weekly pulls (2026-29 through 2026-40) while the actual GSC
> Index Coverage report (last updated 2026-09-20) showed:
>
> | Bucket | Count |
> |---|---|
> | Indexed | 80 |
> | Crawled – currently not indexed | 474 |
> | Discovered – currently not indexed | 172 |
> | Page with redirect | 87 |
> | Alternate page with proper canonical | 31 |
> | Not found (404) | 24 |
> | Other 4xx | 5 |
> | Excluded by noindex | 4 |
>
> Live URL Inspection (2026-10-05) confirmed the homepage, `/celpip/reading/`,
> and `/ebook/` are genuinely indexed and healthy. `/ielts/reading/` is
> "Discovered – currently not indexed," never crawled, with no technical
> blocker on a live test ("available to Google," fetch successful) —
> consistent with a crawl-budget backlog on a young, low-authority domain,
> not a crawl failure. The automated data spine now pulls real per-URL status
> via the URL Inspection API (`urlInspections[]` on the snapshot, wired up
> 2026-10-05, commit `8edd8ac`) specifically because `sitemaps[].indexed` is
> this unreliable — see `.claude/agents/seo-analyst.md` and `cro/README.md`
> for the corrected guidance going forward.
>
> **2. A code-fix claim made in conversation (not in this file) was wrong and
> was retracted before anything shipped.** Analysis of the full 474-URL
> "Crawled – currently not indexed" export (provided by the site owner,
> 2026-10-05) found that 60.3% of it (286 of 474 URLs, 154 pairs) is the same
> page counted twice — once with a trailing slash, once without. The first
> explanation offered for this — that `Layout.astro`'s default
> `canonical = Astro.url.pathname` "echoes back whatever URL was requested"
> — does not hold: this is a statically-generated (SSG) site, so that value
> resolves once per route at **build** time, not per live request. Checking
> the actual route files (`lessons/[category]/[...slug].astro`, which renders
> most of the `/lessons/grammar/*` leaf pages — the single biggest category
> in the export at 200 of 474 raw URLs) showed an explicit, already-correct
> `canonical={".../slug/"}` with a trailing slash; a plain file-based route
> (`celpip/speaking/task-5-comparison/index.astro`) resolves to the same
> trailing-slash form by construction. **No code fix was written or shipped
> for this.** The 60.3% trailing-slash duplication in the export is real and
> numerically confirmed; why Google is parking those pairs in
> "Crawled – currently not indexed" instead of the "Alternate page with
> proper canonical" bucket that exists for exactly this case is still
> unexplained. Next step (not yet done): compare the actual served canonical
> vs. Google's "Google-selected canonical" on one live pair via URL
> Inspection's tested-page result, before any code change is attempted.
>
> Everything else below — the §1 trend tables, §2–4 analysis, and the three
> actions — stands as it was, dated to what the automated snapshot alone
> could show on 2026-10-05, before this additional data arrived.
